# ADR-0001: Technology Stack Selection (Microservices MVP on Raspberry Pi 5)

## Status
Accepted

## Context
We are building a microservices-based e-commerce MVP for Colombia, designed to run on a single-node deployment (Raspberry Pi 5, ARM64).
We want:
- Clear service boundaries (6 services)
- Independent deployability per service
- Simple, maintainable runtime on limited hardware
- Real payment gateway integration (Wompi)
- Minimal infrastructure complexity for MVP

## Decision

### Backend language & framework
- **Python 3.12** for all services
- **FastAPI** as the web framework

Rationale:
- High developer productivity
- Strong typing with Pydantic
- Good async support when needed
- Good ecosystem for building REST APIs

### Data layer
- **PostgreSQL** (one database per service)
- **SQLAlchemy 2.0** (ORM)
- **Alembic** (migrations)

Rationale:
- PostgreSQL is reliable and well-understood
- One DB per service enforces boundaries
- SQLAlchemy + Alembic is stable and flexible

### Authentication
- **JWT (Bearer tokens)**
- Password hashing with **bcrypt**

Rationale:
- Simple stateless auth across microservices
- Fits a gateway + multi-service setup

### Payments
- **Wompi** integration owned exclusively by Payments Service

Rationale:
- Colombia-first payment methods and adoption
- Keeps external gateway complexity isolated

### Inter-service communication
- **Synchronous HTTP** between services (REST)

Rationale:
- MVP simplicity and debuggability
- Avoids broker complexity on Raspberry Pi

### API Gateway / Reverse Proxy
- **Caddy** (recommended) OR **Nginx** as gateway

Rationale:
- Caddy simplifies HTTPS/TLS with automatic certificates (if using a domain)
- Nginx is very standard if you prefer manual TLS setup

### Containerization & orchestration
- **Docker** for containerization
- **Docker Compose** for local + Raspberry Pi deployment

Rationale:
- Raspberry Pi 5 is a single node; Compose is the right level
- Simple operations: start/stop, logs, updates

### Observability (MVP)
- Structured logs (JSON) per service
- Minimal health endpoints per service
- Optional: lightweight metrics later (not required for MVP)

## Alternatives considered
- Node.js/NestJS: strong choice, but team preference is FastAPI and learning focus
- gRPC: better performance and contracts, but adds complexity for MVP
- Kafka: too heavy for Raspberry Pi MVP and early-stage system
- Kubernetes: not suitable for a single Raspberry Pi MVP deployment

## Consequences
### Positive
- Clear, consistent stack across all services
- Low operational overhead on Raspberry Pi
- Easy local development mirroring production (Compose)
- Payment isolation reduces blast radius

### Negative / Risks
- Python microservices on a single node can be resource-heavy if not tuned
- Need to be disciplined with service boundaries (no code-sharing across services)
- Synchronous calls can amplify failures (must implement timeouts + retries later)
