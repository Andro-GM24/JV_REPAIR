# ADR-0002: Auth Service Strategy (JWT EdDSA + Refresh Sessions)

## Status
Accepted

## Context
We are building a microservices MVP (6 services) deployed on a single Raspberry Pi 5 node.
The system requires:
- A single source of truth for identity (users)
- Stateless authentication across services (no per-service sessions)
- Strong cryptographic separation so that compromising one service does not allow forging tokens
- The ability to log out / revoke sessions and limit damage if tokens leak

A “smart gateway” is not assumed. Each service must be able to validate user identity independently.

## Decision

### 1) Token types
We will use **two-token auth**:
- **Access Token**: JWT, short-lived (e.g., 10–15 minutes)
- **Refresh Token**: opaque random token, long-lived (e.g., days), stored server-side in Auth DB

### 2) Signing algorithm (Access Token)
Access Tokens will be signed using **EdDSA** (asymmetric cryptography):
- Auth Service holds the **private key** (signing only)
- Other services hold the **public key** (verification only)

This avoids a shared secret across services.

### 3) Validation model
- Every microservice validates Access Tokens locally using the public key.
- Microservices do **not** call Auth on every request.
- Auth is called only for:
  - login/register
  - refreshing tokens
  - logout (revocation)
  - optional: introspection/admin endpoints (later)

### 4) Session model (Refresh Tokens)
Refresh Tokens represent user “sessions”.
- Stored in Auth Service database
- Rotated on each refresh (refresh-token rotation)
- Revoked on logout
- Can be revoked on suspicious activity (manual/admin)

### 5) Claims (Access Token payload)
Access Token claims are minimal and stable across services:
- `sub`: user identifier
- `role`: authorization role
- `iss`: issuer (Auth Service)
- `aud`: audience (this platform)
- `iat`: issued-at
- `exp`: expiration
- `jti`: unique token id (debugging / auditing)

No sensitive personal data is stored in JWT claims.

### 6) Security requirements
- Passwords stored using strong hashing (bcrypt/argon2; implementation detail)
- Web clients must store tokens securely (implementation detail)
- Refresh tokens must be stored hashed in DB (recommended)
- Auth keys must never be committed to git; loaded via environment/secrets

## Alternatives considered
- **HS256 (shared secret)**: rejected because any compromised service could forge tokens.
- **Long-lived JWTs without refresh**: rejected because revocation is difficult and risk window is large.
- **Gateway-only validation**: rejected for MVP learning goals and because it creates a single enforcement point.

## Consequences

### Positive
- Strong security boundary: only Auth can sign tokens
- Services remain stateless and scalable
- Short-lived access tokens limit damage if leaked
- Refresh tokens enable logout and session revocation

### Negative / Risks
- Requires implementing refresh flow and rotation correctly
- Requires key distribution of the public key to all services
- Time sync matters (token expiry); the node clock must be correct

## Follow-ups
- ADR: Key management and rotation policy (EdDSA keys)
- Auth DB design (users + refresh sessions)
- API contracts for auth endpoints (register/login/refresh/logout)

# Auth Service — Mental Model

## What it is
Auth Service is the **identity authority** of the platform.
It is the only component allowed to:
- create valid Access Tokens (signing with EdDSA private key)
- manage user sessions (refresh tokens)
- revoke sessions (logout)

## What it is NOT
Auth Service is not:
- a gateway or proxy
- a per-request dependency for other services
- a place to store business data (orders, products, stock, payments)

## Core objects (conceptual)
- **User**: an account with credentials and a role
- **Access Token (JWT)**: short-lived proof of identity, signed by Auth
- **Refresh Token (Session)**: long-lived session handle, stored and revocable in Auth DB

## Invariants (rules that must always hold)
1) Only Auth has the EdDSA private key.
2) All other services only have the public key and can only verify tokens.
3) Access tokens are short-lived to reduce risk if stolen.
4) Refresh tokens are stored server-side and can be revoked.
5) Refresh token rotation is enforced: using a refresh token replaces it with a new one.
6) JWT claims remain minimal and stable across services.

## System boundary and trust
- Client trusts Auth to issue tokens.
- Services trust Auth’s signature (via public key).
- Services do not trust other services to issue tokens.

## Typical flows (conceptual)

### Login
User proves credentials to Auth.
Auth returns:
- short-lived access token (JWT signed with EdDSA)
- long-lived refresh token (opaque session)

### Request to any service
Client sends access token.
Service verifies:
- signature (public key)
- expiration (exp)
- issuer/audience
Then authorizes using minimal claims (sub, role).

### Refresh
Client sends refresh token to Auth.
Auth verifies session state in DB, rotates refresh token, returns new access token + new refresh token.

### Logout
Client requests logout.
Auth revokes the refresh token session so it cannot be used again.

## Cross-service authorization principle
Authorization decisions should be made using:
- minimal token claims (role + sub)
- service-owned data (when needed)
Avoid embedding complex permissions or business state in JWT claims.
